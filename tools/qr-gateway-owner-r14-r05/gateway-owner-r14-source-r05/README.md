# R05: reparación acotada del rollback, sólo local

R04 y `pack-r04` se conservan byte-exactos. Esta revisión cambia únicamente dos comportamientos de fallo del applier y el argumento interno que permite comprobar identidad/configuración del candidato sin exigir la red que falló. No cambia runtime, diez archivos compilados, catorce payloads fuente, imagen, permisos, plazos, secuencia sana, perfil FALSE o credenciales.

El handler usa directamente el ID ya asignado cuando ocurrió un fallo posterior a la creación; una lectura global de Docker no puede impedir restaurar los IDs conocidos. Sólo una respuesta de creación desconocida intenta UNA lectura de descubrimiento por el nombre exclusivo y la imagen/label del intento. Un descubrimiento desconocido queda registrado sin retry ni start/stop.

Para el rollback después de `stop_attempted`, el candidato ya pasó la validación STOPPED completa antes de parar el original. Se exige otra vez su ID/nombre propio, imagen, label, Config, HostConfig y doce mounts exactos. Su red activa no se presume equivalente ni se usa para autorizar un stop: puede ser precisamente el motivo de rechazo. Ningún candidato de imagen/configuración distinta se detiene. La verificación de red completa sigue intacta en la vía sana.

Las cuatro pruebas locales son nuevas y usan puertos Docker stateful falsos: health falla con listado indisponible; aliases de red fallan después de start; create desconocido más descubrimiento fallido; imagen de candidato alterada que debe conservarse sin stop. No ejecutan Docker/red ni leen perfiles/credenciales reales. No se repiten las once pruebas owner cerradas.
